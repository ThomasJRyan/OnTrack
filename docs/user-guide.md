# User guide

ontrack browses Beads issues in a two-pane terminal view and can create, edit, or permanently delete one issue at a time. It uses the public `bd` CLI and the current working directory to select the workspace. It does not access the Beads database directly.

## Requirements and startup

- Rust 1.88 or newer to build this Rust 2024 project.
- `bd` available on `PATH`, with support for the JSON commands shown in the [development guide](development.md#beads-cli-contract).
- Run the browser from a Herdr-managed shell, which supplies `HERDR_ENV=1`. Outside Herdr, OnTrack exits before Beads discovery or terminal setup and tells you to open a Herdr workspace. `--help`, `update`, and `uninstall` remain available outside Herdr.
- If no Beads workspace is accessible from the launch directory, OnTrack tells you to run **`bd init`** and exits. Existing workspaces, including inherited and redirected ones, are reused with their configuration intact.
- An interactive terminal supporting raw mode and the alternate screen; mouse support is needed for clicking and wheel input.
- For `ontrack update`, `curl` and `tar` must be on `PATH`, and the executable's directory must be writable for replacement. This command needs neither Herdr nor a Beads workspace.

See the [official Beads documentation](https://beads.gascity.com) for installing `bd` and setting up a workspace. For supported binary downloads and checksum verification, see the [release guide](releases.md).

From this repository, when it is the workspace you want to browse:

```sh
cargo run
```

To browse another workspace, build with `cargo build`, change to that workspace, and launch the built binary using its absolute path. The launch directory, not the binary's location, determines which workspace `bd` uses. Do not launch the interactive application in a runner without a terminal.

After confirming the Herdr launch marker and before opening the terminal interface, OnTrack asks Beads to locate the active workspace. If none exists, it prints “No Beads workspace found. Run bd init in your project, then launch OnTrack again.” and exits successfully. The command **`bd init`** appears in bold on terminal stdout; redirected output contains plain text. OnTrack does not ask setup questions, read input, initialize Beads, or change its configuration. Initialize the workspace yourself, then launch OnTrack again.

Existing workspaces retain their configuration, including JSONL auto-export. OnTrack preferences such as theme, default agent, agent limit and cleanup remain available with `s` in the browser.

If `bd` is missing or workspace discovery fails, OnTrack stops before raw mode and reports the launch directory and failing step. Discovery, permission, and database failures do not trigger initialization guidance or replacement initialization.

A brief splash precedes the browser. A terminal-drawn anime girl blinks and waves beneath the ONTRACK wordmark; narrower terminals use a compact title, and very small terminals show text only. The animation lasts about 1.2 seconds and uses the selected theme. Issue loading starts in the background; quit keys work during startup too.


## Your first task

Once the browser opens in your Herdr project workspace:

1. Use `↑` / `↓` to select a Bead and `Tab` to focus its details. The arrow keys then scroll the description, comments, and relationships; `Tab` returns to the list.
2. Press `n` to create a task, or `e` to refine the selected Bead. Give the agent a clear description and choose its harness. Use `Shift+N` on an open task to split off a child task.
3. Press `r` to mark the task Ready for automatic scheduling. Run the scheduler from the main checkout; it waits for eligible work, an available agent slot, and a usable harness. For an immediate manual handoff, press `h`.
4. Press `w` to follow the tracked worktree. `Enter` opens its Herdr workspace. When the work is ready, `m` requests a merge; inspect the result before using `c` or `x` to close the integrated workspace or remove its checkout. Return to the issue browser with `Esc`.

Press `Ctrl+?` whenever you need the controls for the current view. See the scheduling and worktree sections below for eligibility, confirmation, and recovery details.

## Status groups

All bordered panes and dialogs, including tracked handoffs, forms, planning, and hotkey help, use rounded corners.

Issues are shown in rounded, colour-coded panes. Open, Ready, Blocked, Deferred, In Progress, and Closed remain visible with a count of zero when empty, even when the workspace has no issues. Open appears first and Closed last; other and unrecognized statuses appear alphabetically between Ready and Closed when issues have those statuses. An empty status is labelled Unknown only when an issue has one. The Closed group starts collapsed after the first list loads; other groups start expanded. Pane titles show the status and count. Each issue's type, priority, and status columns align across groups; the selected issue's details pane title shows its ID, status, and priority. Use `↑` / `↓` to move through visible issues, empty group headers, and collapsed group headers. Expanded headers with issues are skipped. Movement clamps at the first and last target. A focused header is highlighted and does not select an issue or retain detail/delete identity. Press `Right` or `Space` on a collapsed header to expand the group and select its first issue when one exists; an empty header stays focused. `Left` collapses a group. Press `Space` on a selected issue or use `←` / `→` to collapse or expand its group; clicking a pane title also toggles that group. Collapsing a selected issue's group selects its collapsed header. Mouse title clicks can reopen any group. Refresh preserves focus on a collapsed or empty header while that group exists.

Ready group borders and Ready status text are blue in every theme. The label remains visible alongside the colour.

## Browsing and controls

### Plan new work with an agent

Press `p` from the issue browser to plan a new Task or Epic. Type a proposal and press `Enter` to start the agent in a new tab of the current Herdr workspace. `Shift+Enter` adds a line break in the proposal on terminals that report modified Enter. Planning does not edit the selected issue or create Beads yet.

OnTrack gives the planning agent a Herdr-compatible lowercase name when it starts. For Codex, it passes a session-only trust setting for the verified main Git repository, including when planning from a linked worktree, and defers the startup update check. It also trusts enabled hooks for this invocation, avoiding folder and hook trust prompts without changing your saved Codex settings or permission policy. If agent startup fails for another reason, the new tab stays open so you can inspect it before retrying.

When the agent asks a question, use `Up` / `Down` to select one of its answers and `Enter` to send it. Select **Custom answer** with `Tab` or `Down` and type your own answer. The agent continues in the background; its next question or proposed plan appears in OnTrack. The agent may take a while to respond. It is instructed to use a structured response, so an agent that ignores that instruction may need attention in its Herdr tab.

Review the proposed title, description, acceptance criteria, priority, and any child Tasks. Scroll a long plan with `Up` / `Down` or `PageUp` / `PageDown`. Press `r` to request a revision, then type your instruction and press `Enter`. Press `y` only when the plan is ready: OnTrack then creates one Task, or an Epic with child Tasks. New Tasks start Open and Unassigned, so you can select an agent and mark them Ready later. Press `Esc` to cancel without creating Beads. The Herdr planning tab remains open for review; close it from Herdr when no longer needed.

If creation reports an error, inspect the named Beads before planning again. An Epic and some children may already exist, and retrying the same plan could duplicate them. OnTrack refreshes the browser after a creation attempt.

### Ready issues and scheduler

Press `r` on an open issue of any type to mark it Ready; press it again to return an unsent Ready issue to Open. `Shift+R` also works in the issue browser. An issue showing `· sent` stays Ready while its Beads status is open, and OnTrack shows a notice if you try to clear it. Ready also cannot be cleared while its handoff is underway or before tracked handoffs have loaded. Prepared or uncertain handoffs without a confirmed sent prompt can still be turned off for recovery. On an open issue with children, either key marks the parent and all its open descendants Ready, including nested children of any issue type. Press it again on an unsent parent to clear Ready from the parent and its unsent descendants; sent or pending descendants stay Ready. Closed descendants and descendants with other Beads statuses are left alone; open children beneath them are still included. Issues already tracked as handed off are not marked Ready again. Ready is an OnTrack group between Open and the other Beads statuses. The underlying Beads status stays `open`; OnTrack stores the marker as the `ontrack:ready` label.

Ready changes run in the background, including large Epic cascades. The header shows “Updating Ready for ID…” while processing. You can keep navigating, scrolling, opening help, switching to worktrees, or quitting. Additional Ready changes, mutation dialogs, manual handoffs, and automatic scheduling wait until the update finishes. Confirmed changes appear when processing completes, followed by a live refresh; failures also refresh to show any partially applied changes. Quitting does not cancel a running Ready update.

The new issue form has an Agent harness choice after Priority for every type. It checks Herdr in the background and lists only supported kinds whose integration is current, plus Unassigned. The Default agent for new issues setting controls its initial choice: Automatic selects Codex when available, otherwise the first available kind. A saved agent that is unavailable uses the Automatic fallback for that form without changing the setting. Unassigned starts with no agent selected. This also applies to new child Tasks. Wait for the check before creating an issue. If Herdr cannot be queried or no current integration is found, the form shows the reason and offers Unassigned only; create remains available after the check. A selected agent is saved as an `ontrack:agent:KIND` label; explicit Unassigned is saved as `ontrack:unassigned`. Edit keeps an existing harness choice even if its integration is no longer current. Ready issues with an unavailable selected harness or explicit Unassigned choice do not launch. Older or externally created Ready issues with neither label use the configured default agent when available, falling back to Codex or the first available integration.

New child tasks keep ordinary labels from their parent, but start Open with their own harness selection; they do not inherit the parent's Ready marker, harness choice, or explicit Unassigned marker.

While OnTrack is running from a Herdr main checkout, its scheduler prepares a Ready parent's managed checkout when it has eligible Ready non-Epic descendants, then picks eligible Ready non-Epic issues by Beads priority and ID. Preparing a parent does not start its agent or consume an agent slot. Nested parent checkouts are prepared from the root down so each child branches from its immediate parent. Agents then work from the leaves up: each parent waits until its descendants close and its child worktrees integrate. The scheduler waits for the managed-worktree scan, checks that the chosen harness has a current Herdr integration, and uses the same tracked launch path as `h`. A successful agent handoff leaves an open issue in Ready until its Beads status changes. A prepared parent resumes after its children close and integrate; a prepared Epic can be handed off with `h` after its children integrate. Marking a parent Ready also marks its open descendants Ready for automatic child scheduling; the child waits until the parent's managed checkout exists. Failed or uncertain attempts show an error and are not retried repeatedly in the same app session. To retry after fixing the cause, turn Ready off and on; inspect `w` first if a worktree may already exist. Starting OnTrack again retries Ready issues that have no recorded handoff.

The scheduler starts at most five active agents by default. Press `s` and change **Agent limit** to Unlimited or a positive count to set another limit. The choices run Unlimited, 1, 2, 3, and upward. Active tracked handoffs count against the limit even when you started them with `h`; prepared parent worktrees and finished handoffs do not. At the limit, Ready issues wait in their existing priority order until a slot opens. Manual `h` handoffs remain available and can exceed the limit. See the [settings guide](settings.md) for the saved format.

The left pane lists all returned issues, including closed ones, without the CLI's usual list cap. Each entry shows its colour-coded issue type, priority, status, and a white title; the selected issue's ID appears in the details pane title. The rounded details pane shares the issue list's theme background. Its title shows the selected issue's ID, status, and P0–P4 priority; those fields are omitted from the body. It presents narrative fields as Markdown, while other metadata, comments, relationships, and unfamiliar nested values remain available as you scroll.

Within a status pane, a parent appears before its children and nested children are indented beneath it. Both lines of each entry move two spaces to the right per nesting level: roots have no added indentation, children have two spaces, grandchildren have four, and so on. In narrow panes, indentation stops increasing when needed to leave room for row text. A child whose parent is in another status pane or absent from the current list stays in its own pane and shows the parent ID before its title. Status panes still control collapse and navigation; indentation does not change a Bead's status or parent relationship.

An Open or Ready issue shows `· sent` beside its status after Herdr confirms the initial agent prompt and OnTrack saves the handoff. The marker survives refresh and restart through the tracked worktree record. The Beads status remains `open` until the agent changes it; a Ready issue then appears under its new status, and the sent marker disappears. A handoff without confirmed prompt submission does not show the marker. Use `w` to inspect any incomplete or uncertain launch.

Inside the create and edit forms, keys are text unless they are form controls; app shortcuts do not trigger, and arrow keys continue to edit text or choose options. Dropdowns share one rule: Left / Right cycles choices with wraparound, whether the dropdown is closed or open. In text fields, Left / Right retain their cursor-editing behavior. Description wraps at word boundaries, splitting only words wider than the field. In Description, Up / Down moves the caret through the visible lines, including wrapped lines and lines separated by Shift+Enter. The caret keeps its display column when possible and stops at the first or last line. Shift+Enter requires a terminal that reports modified Enter keys; in terminals without that support, it may arrive as plain Enter. New beads default to Task and P2; the harness default follows the saved setting and current Herdr discovery. The edit form loads the latest `bd show` record before opening and preserves fields outside its five controls. Beads with unsupported types or priorities cannot be opened in the edit form. A mutation runs once at a time in the background; the modal is locked until it finishes. Failures remain visible and keep the form open for correction or retry. Successful creation refreshes the list and selects the new bead; successful edit refreshes the list and detail while retaining the edited bead. Dialogs ask you to enlarge a terminal that is too small to show the full controls and warnings.

With Description focused, copy a PNG or JPEG screenshot and press `Ctrl+V`. OnTrack reads the image from the local Wayland clipboard with `wl-paste` or the X11 clipboard with `xclip`, saves it under the shared Beads workspace in `.beads/screenshots/`, and inserts a Markdown image reference at the caret. Wait for the saved-image message before submitting the form. Esc discards screenshots pasted in an unsaved form. An unavailable image or clipboard tool shows an error and leaves the text unchanged. Screenshots remain local to this machine; they are not carried by Beads JSON export or Git commits. Keep the shared Beads workspace and its screenshot files available while agents need them.

The hotkey reference accepts terminal reports of `Ctrl+?`, `Ctrl+Shift+/`, and `Ctrl+/`. Some terminals send the same unmodified Backspace code for `Ctrl+?`; on those terminals the app cannot distinguish the keys, so use a terminal with modified-key reporting. The reference is unavailable while a mutation locks its dialog.

Automatic merge may defer when there is no trustworthy evidence that the agent is idle; a closed Bead alone never proves it is safe to merge. Removing a checkout also closes its Herdr workspace. Settings load/save errors remain visible; failed saves preserve the last successfully saved settings. See the [settings guide](settings.md) for recovery.

## Generate tasks for an Epic

Mixed-case Epic IDs are supported. OnTrack uses a lowercase agent alias for Herdr while retaining the original Epic ID for the generated tasks' parent.

In the create form, choose **Epic** to reveal **Generate child tasks with a Herdr agent** below Description. Tab moves from Agent harness through Description to this option, then Create. The option starts off. Enter the proposal in Description, turn on the option, and create the Epic. OnTrack saves the Epic first, then opens a planning tab inside the current Herdr workspace at the current checkout, starts an available agent, and asks it to create direct child Beads with descriptions, acceptance criteria, and explicit P0–P4 priorities. The agent compares impact, urgency, and enabling work to distinguish priorities when the proposal supports it; comparable or unclear tasks may share a priority. Review the generated priorities before scheduling tasks. It does not create another Git worktree or top-level Herdr workspace. The form hides and clears this option for other issue types; editing a Bead does not run generation.

To generate tasks after creation, select an Epic in either issue pane and press `g`. The shortcut appears only for Epics. The confirmation names the Epic and warns that existing children remain and another run may add duplicates. Press `y` to start or `n`, Enter, or Esc to cancel. Add a Description first if the proposal is empty. Repeated requests for the same Epic are blocked while planning runs in this OnTrack process. Editing alone still does not trigger generation.

For Codex, OnTrack handles the first-directory trust check for the verified main Git repository and defers the startup update check for this planning session. This also works when the current checkout is a linked worktree. Enabled hooks are also trusted for this invocation. These settings apply only to the launched process; update Codex separately when convenient. Other agent integrations keep their normal startup settings. Authentication, administrator policy, or an unfamiliar startup dialog can still require your input. If startup fails, the error identifies the workspace, tab, and pane and confirms that no planning prompt was sent. Inspect that pane and resolve the input before retrying generation.

Keep OnTrack open while planning runs. The top-right message reports launch, completion, or a recovery error. After the agent finishes, OnTrack checks that at least one direct child exists and closes only the planning tab. If the agent exits after creating children, OnTrack also accepts completion when Herdr confirms that its original pane is still present with no agent. If creation, agent start, prompt delivery, or child verification fails, the Epic remains. An already created planning tab stays open so you can inspect its agent and Beads. Check that tab before retrying; a prompt failure may still have delivered the proposal, and another run can duplicate children. If the planning tab becomes the last tab in the workspace, OnTrack leaves it open to preserve the workspace. This workflow requires OnTrack to run inside Herdr with a current agent integration.

## Details, loading, and refresh

Selecting an issue immediately displays its cached list record while a richer `bd show` request runs. The returned detail record replaces that snapshot. ontrack requests long details, comments, and dependents; descriptions, notes, design and acceptance text render as Markdown. Metadata, comments, relationships, and unknown nested values are shown whenever present in the returned JSON, except for the top-level revision field. It does not invent missing fields or fetch data outside those CLI responses. Scroll the details pane to see fields below the visible area.

Dependencies appear as a compact flow chart rooted at the selected Bead. **Blocked by ← prerequisites** lists issues that block the selected Bead; **Blocks → dependents** lists issues the selected Bead blocks. Blocking groups appear first. **Parents** and **Children** show hierarchy separately; other link types retain their type and source field without claiming blocking semantics. Solid branches and node headers use the issue's priority color from your theme, with explicit P0–P4 labels when available; missing priorities are neutral. Each node shows its ID, status and full title without repeated boxes. Eight typical children fit in about 20 chart rows at 100 columns. The chart shows direct returned links, including closed issues, rather than loading a recursive tree. Long labels wrap, tiny panes omit indentation, and larger graphs use the usual detail scrolling. Additional fields and unsupported records remain under **Relationship Details**. Empty returned relationship arrays show “No dependency links returned”; absent fields do not imply that the Bead has no dependencies.

ontrack automatically polls the issue list and selected issue's details in the background, starting another refresh roughly one second after the previous refresh completes. Changes made by another terminal or agent appear without manual input or configuring events, a watcher, or extra dependencies. Slow `bd` commands increase the delay; updates are not instantaneous or event-driven. Successful create/edit/delete actions in ontrack still trigger an immediate refresh. In the separate `w` view, `r` still refreshes tracked worktrees.

The issue-browser footer always shows short action hints and points to `Ctrl+?` for the full key reference. It does not repeat routine ready or loading state or arrow-key navigation. Errors and action notices appear on the second header row without replacing the shortcuts. The tracked-worktrees footer is one row tall and shows shortcuts for focus, merge, close, remove, continue, restart, detail scrolling, and hotkey help. It omits refresh, worktree selection, quit, and return hints; those keys still work and appear in the full `Ctrl+?` reference. Narrow terminals show the shortcuts that fit. Worktree errors and focus feedback appear on the second header row, while confirmation instructions stay in their dialogs. Selected-worktree status and details stay in their panes. Refresh retains the existing list while loading and keeps the selected ID if it still exists in the new list; otherwise it selects the first issue. Automatic updates preserve group collapse state, pane focus, scroll position within available content, and active form input. A failed list or detail refresh keeps the last loaded data (or the available list snapshot) visible alongside the error and retries automatically after the cause is resolved. An empty successful list displays “No issues found in this workspace.”

## Update OnTrack

Run `ontrack update` from a normal terminal, in any directory. It prints the
running version and checks the [latest stable OnTrack release](https://github.com/ThomasJRyan/OnTrack/releases).
If the version is current or no release is published, it reports that and exits.
If a compatible newer release is available, it prints the version and release
link, then asks `Install this verified release? [y/N]`. Enter `y` or `yes` to
install; any other answer, including Enter alone, cancels before replacement.
The command does not start the browser or require Herdr or Beads.

The updater selects an asset for the current operating system and architecture,
downloads its published `.sha256` checksum, verifies the archive, and stages
replacement beside the running executable. A missing compatible asset,
checksum mismatch, network error, missing `curl`/`tar`, or unwritable install
directory returns an error. The existing executable remains usable if the
command fails before replacement; rerun `ontrack update` after fixing the cause.
The updater does not install Beads or Herdr. Restart any OnTrack session already
running after success; that session continues using its original code.

## Launch an agent with Herdr

Run ontrack inside a running [Herdr](https://herdr.dev/docs) shell in a Git checkout. Herdr must supply `HERDR_ENV=1`; `herdr` and the selected agent executable must be on `PATH`, and that agent's Herdr integration must already be installed and current. ontrack does not install integrations or grant Git safe-directory trust automatically.

Codex launches trust the verified main repository and disable startup update checks **for that invocation only**; no global configuration is changed. Source and new-worktree Git metadata must agree before Codex starts. OnTrack also passes `--dangerously-bypass-hook-trust`, so enabled user, project, session, and plugin hooks can run without a separate review for this invocation. Starting a Codex session through OnTrack therefore assumes you trust those hook sources. Saved hook approvals, sandbox settings, and tool approval policy are unchanged. Use a Codex version supporting this flag (verified with 0.163.0). OpenCode startup is unchanged. Authentication, administrator policy or unknown startup prompts may still need your attention; ontrack does not bypass them. Nonstandard or mismatched Git metadata stops startup safely and preserves any created worktree for inspection.

Handoff uses the selected bead and its mapped Herdr workspace, not global window focus. Pressing `h` starts discovery and launch without further input. If the Bead has an agent harness choice, OnTrack requires that exact current Herdr integration. Older Beads without a choice use Codex when available, then the first available integration. Discovery failure can be retried with `h` after resolving the cause. A valid launch creates a worktree from committed checkout content only, starts the chosen integration, and sends the issue context with instructions to inspect the authoritative bead and project guidance. The prompt asks the agent to commit and check finished work, then close the Bead as its completion signal. Blocked or unfinished work keeps the Bead open or in progress and reports the blocker.

If the description contains screenshots pasted through OnTrack, the initial agent prompt lists their local file paths and asks the agent to inspect them. Herdr sends a text prompt, so the image bytes stay in the shared Beads workspace; the new worktree can read them from there on the same machine.

For child tasks, press `h` on the parent after creating children. OnTrack prepares its worktree without starting an agent while children are open or their worktrees await integration. Then hand off each child; it starts from the parent branch, and its merge target is the parent worktree. The tracked-worktrees list places child handoffs directly beneath their parent with indentation. After a child's Bead closes and its agent settles, OnTrack requests merge into the parent worktree automatically by default, including for Epic subtasks and nested children. Keep OnTrack running so reconciliation can finish. The Settings switch “Auto-merge child tasks into parent” turns these automatic requests off; `m` remains available for a confirmed manual request. The independent top-level automatic merge switch remains off by default. Git, agent, and Beads safety checks still apply; a conflict or uncertain result stays visible for recovery. Once each child is integrated, press `h` on the parent again to start its agent in the prepared worktree. Parent merge requests also wait for children. A child may exist in Beads before the parent worktree is ready; its handoff will ask you to prepare the parent first. Beads itself still lists the parent as ready: it disallows a blocking edge from a parent to its own descendant because that would also block the child. OnTrack enforces the child-first rule for its handoffs and merges; external Beads clients do not inherit this gate. An agent started on a parent before a new child is added cannot be paused automatically; OnTrack still blocks parent integration until the child is complete. Keep the parent checkout clean before starting or integrating a child. Remove child checkouts before closing or removing the managed parent checkout.

Only new handoffs recorded by OnTrack are managed in the outstanding-worktrees view; pre-existing worktrees are not adopted. The target branch comes from verified repository state and is shown before a merge request. Git integration—not Beads status—determines whether work is integrated. Conflicts and uncertain outcomes remain visible for manual recovery. Cleanup never force-removes a checkout or removes its branch.

Worktree discovery runs quietly in the background. The list stays blank during an initial scan and keeps existing rows visible during refresh. Empty-state guidance appears after a scan completes with no outstanding handoffs and stays visible during automatic refreshes, manual refreshes, and error retries without blinking; scan errors still appear in the header.

An active checkout shows `IN PROGRESS` while its Bead is open or the recorded agent has not been verified as finished, even after commits appear on the task branch. It shows `READY TO MERGE` when the Bead is closed, the recorded agent has settled after prompt activity, and the clean task branch has commits outstanding against its target. Older handoffs whose launch response lacked a native agent session can use their recorded pre-prompt Herdr observation for this display state when the same pane and terminal report later activity. Automatic reconciliation can bind a later matching native session before merging; if that evidence is unavailable, use a confirmed manual merge after reviewing the work. An unavailable Bead, working or mismatched agent, missing activity evidence, or untouched branch does not claim readiness. `READY TO MERGE` means the task work awaits integration, not that it has already merged. Manual merge requests remain available with confirmation, while the existing Git and agent checks decide whether the request can proceed.

If Herdr confirms that the recorded agent session is `blocked` or `error`, an otherwise `IN PROGRESS` tracked checkout shows `BLOCKED` and the details name the observed state. The label returns to `IN PROGRESS` when that observation clears or becomes unavailable. Git states such as uncommitted changes, merge conflicts, and completed integration keep their own labels. This display label does not change the Bead's status or grant permission to merge, retry, or clean up; inspect the agent pane and Bead to recover the task.

In the `w` view, select a handoff with Up / Down and press Enter to switch to its recorded Herdr workspace. This uses the existing workspace; it does not create or reopen one. Closed workspaces cannot be focused, and Herdr errors appear in the view. The right pane shows its Bead title and description from the refreshed Beads list when available, plus the current worktree state and Git/Herdr details. If the Bead is unavailable, the pane uses the title and description captured at handoff. Older handoffs without captured text show an unavailable-text message; a Bead without a description shows the same fallback. PageUp / PageDown or the mouse wheel over the right pane scrolls long descriptions. Press `m` to request a merge, `c` to close its integrated Herdr workspace, or `x` to remove its integrated checkout; each action requires `y` confirmation. Manual and automatic requests enter a durable repository queue. `MERGE QUEUED` waits while another OnTrack merge is active; only the first request is sent to its agent. Once that request is verified integrated and its agent has settled, the next is checked against current Git, Beads, and Herdr state before dispatch. A merge needing resolution or an uncertain prompt holds the queue until explicitly recovered. A queued request with a review error can be retried with `m` after fixing its cause. The agent merges the target into the task branch and resolves conflicts there; OnTrack then verifies current Git history and fast-forwards the target. Keep OnTrack running for reconciliation. Press `r` to refresh or `w` to return to Beads.

Press `a` on an active tracked handoff to ask its original idle agent to continue in the same checkout. Confirm with `y`; `n`, Enter, or Esc cancels. OnTrack checks the live Bead, checkout and Herdr workspace ownership, native agent session, idle state, and agent checkout paths before sending one prompt. It preserves commits and uncommitted changes. If the agent exited, changed session, is busy, or cannot be verified, inspect its Herdr pane or use the confirmed fresh start below. If prompt delivery is uncertain, the row stays Needs Attention across restarts and OnTrack will not send another prompt; inspect Herdr before manual recovery. This action does not close the Bead or authorize a merge.

Press `Shift+R` on an active tracked handoff to restart its task. The dialog identifies the handoff and warns that confirmation with `y` discards all uncommitted checkout changes and closes the current Herdr workspace; `n`, Enter, or Esc cancels without touching Git or Herdr. OnTrack verifies the recorded checkout and workspace, force-removes that worktree, and launches the same live Bead with the recorded agent in a fresh branch from the current main checkout HEAD. The Bead and its status are retained, and the abandoned branch is kept for recovery. Restart is independent of integration status, unlike normal cleanup. If removal or relaunch is uncertain, the old record remains visible as Needs Attention; inspect the reported Herdr and Git state before taking manual recovery action. OnTrack never blindly repeats a restart.

Once OnTrack verifies checkout removal, that handoff leaves the `w` view immediately and stays hidden after refresh or restart. The record remains in the local registry. A removed child stays hidden after its parent Epic checkout is merged and removed: OnTrack checks the retained child and parent branches to confirm the child is still integrated. If the child branch gains new commits, a recorded path reappears, or that history cannot be verified, its `NEEDS ATTENTION` status makes it visible again. A closed Herdr workspace with its checkout still present remains visible.

OnTrack also checks recorded checkout paths during its regular worktree refresh. If a managed checkout was removed with Git or another external action, it records the missing checkout and removes it from `w` without requiring an automatic cleanup preference. This only tracks the checkout path: the source branch is retained, and its commits may still need integration. Check Git history before deleting that branch. A path that reappears is shown as `NEEDS ATTENTION` for identity review.

Worktree statuses appear as coloured text in both the list and details, on the pane's normal background. Merge Pending uses the theme warning colour, Integrated uses success, and states needing attention use danger. Other labels use the theme's info, secondary accent, or muted colours. The words remain visible, including when a row is selected, so colour is not the only state cue.

Ordinary uncommitted changes in either the task checkout or its target show `UNCOMMITTED CHANGES`, rather than `NEEDS ATTENTION`. The detail asks you to commit or resolve them before merging or cleanup. A merge request already in flight stays `MERGE PENDING` and includes the same warning. These labels do not make a dirty checkout eligible for a merge or cleanup; those actions still check that both checkouts are clean. Checkout identity errors and unfinished Git operations continue to need attention, and unresolved merge conflicts retain `NEEDS RESOLUTION` during a merge request.

During a requested merge, Git may briefly contain unresolved files or the target branch may advance while the agent is still working. When Herdr confirms the recorded agent is working, OnTrack keeps the label at `MERGE PENDING` and shows the Git concern in the details. If the agent is idle, done, blocked, or cannot be verified, the same unresolved Git state shows `NEEDS RESOLUTION`. That label calls for inspection; it does not mean OnTrack has verified that the agent failed. A pending label does not make the worktree eligible for integration or cleanup.

An unfinished merge of the recorded target HEAD in a managed source checkout shows `MERGE IN PROGRESS` even when it was started outside an OnTrack merge request. The detail distinguishes unresolved conflicts from an unfinished merge without conflicts. This label describes Git state; resolve and commit or abort the merge before requesting integration. A merge against another commit, an unfinished operation in the target checkout, or an invalid checkout identity still needs attention. OnTrack merge requests continue to use `MERGE PENDING` and `NEEDS RESOLUTION` as described above.

Agents can report activity from their managed source checkout with `ontrack status working`, `ontrack status merging`, or `ontrack status blocked 'brief reason'`. Run `ontrack status clear` when the activity ends. A detail is optional for working and merging and limited to 200 characters on one line. The report appears in the tracked-worktree details for 15 minutes, then expires unless refreshed. The command refuses an unmanaged, inactive, or mismatched checkout. Reports are advisory and never change Beads, Git, merge eligibility, or cleanup eligibility. If `ontrack` is not on the agent's PATH, invoke the installed executable by its absolute path.

Untouched branches with no task commits are not automatically considered complete. Herdr can report the native agent session after startup; OnTrack recognizes it on a later refresh when the saved launch terminal, lifecycle activity, and checkout still match. If that evidence is missing or changes, automatic operations defer and the worktree details show why. An explicitly confirmed manual merge can use Git verification without optional session metadata. Removal also closes an open Herdr workspace, so enable removal before closing if both are wanted. Removal after a workspace has already been closed is unsupported: inspect the reported checkout, verify its current changes are integrated and clean, then use Git's exact-path, non-force worktree removal manually. OnTrack never guesses a replacement workspace ID.

Title-only or incomplete beads are supported: the agent is instructed to infer a useful description, scoped requirements and testable acceptance criteria from the live bead and project context, record assumptions, and save missing fields with `bd update` before implementation. It must preserve existing requirements, avoid unrelated scope, and not refuse solely because description or criteria are missing. Only consequential ambiguity unresolved by context warrants clarification; useful inferred details, assumptions and questions should still be saved first. ontrack sends these instructions rather than generating fields itself; handoff success does not prove the agent followed them.

Start ontrack from the **main checkout** (or an ordinary subdirectory) to hand off work. Launch discovery from existing linked checkouts, submodules or nested repositories is unsupported and stops before creation; Herdr 0.9.1 reports the main source checkout for linked paths, so ontrack will not guess a linked workspace. Newly created worktrees remain the verified targets for agent startup.

Contributors can run `cargo test` from a linked Git worktree. The Herdr test fixtures model a main checkout independently of the directory where Cargo runs; this test support does not change the launch restriction above.

The new checkout contains committed Git content only; uncommitted changes are not copied. A successful handoff does not mean the agent completed the bead. Failures may leave a worktree or may have delivered a prompt. Inspect Herdr/Git worktree lists and the reported workspace/branch before retrying; nothing is automatically deleted or blindly resubmitted.

The top-right toast stays visible during discovery and launch, then shows success for seven seconds or failure for fifteen seconds. A successful agent handoff reports the agent, workspace, pane, and branch. The second header row also shows the result or error while space permits, and `w` shows recorded worktrees for recovery. Compact terminals shorten the toast with a pointer to tracked worktrees. If a failure may have created a worktree or sent a prompt, inspect the recorded and Herdr/Git state before pressing `h` again.

Discovery and each handoff run independently of browsing and managed-worktree actions. You can select another Open task and press `h` while an earlier handoff is still running. The newest handoff owns the toast; an older result does not clear another pending launch. While handoffs are pending, tracked-worktree refreshes use a read-only snapshot so display checks do not hold the registry lock needed to record another launch. Ready scheduling includes pending manual/automatic launches in the agent limit and protects all pending Tasks from Ready removal; preparing a parent checkout without starting an agent does not consume a slot. Durable worktree records and recovery evidence survive restart; only pending/toast state is session-local. A managed merge can still hold the shared registry lock: launch journal writes retry contention for about two seconds, then fail safely rather than bypassing it.

The `w` details include a separate display-only agent observation such as working, blocked, idle, error, or unknown. It is refreshed independently about two seconds after each poll completes. Missing or mismatched recorded-session evidence and poll failures show unknown without discarding the worktree or recovery details. An agent observation—even done—is not proof the Bead completed, and never authorizes retry, merge, or cleanup; the existing Git, Beads, and original-agent safety checks still apply.

Backend work does not run on the terminal input loop, so browsing remains responsive while a command is slow. Handoff keeps the browser usable; create, edit, and delete mutations still lock their dialogs until a result arrives. Worker requests are queued and executed in order without coalescing. Quitting restores raw-mode, mouse-capture, and alternate-screen settings through the application's cleanup path.

## Troubleshooting

- **“Could not run bd”**: check that `bd` is installed and on the launch environment's `PATH`, including when starting from an editor or a different shell.
- **“bd failed” / workspace or database errors**: check the error text and launch directory. Run the read-only list command below from that same directory to diagnose the CLI separately; consult the official Beads documentation for workspace access or setup.
- **Unknown CLI options**: ensure your `bd` supports `--readonly`, uncapped listing, and the detail flags in the development guide. ontrack reports failures rather than silently dropping those flags.
- **Invalid JSON or malformed records**: list/show responses must be JSON arrays; creation must return an object with an ID. List entries need nonempty string IDs, titles, and statuses. Check the command output and your CLI version.
- **“expand terminal” / clipped content**: enlarge the terminal. Very small terminals show an expansion prompt instead of the two panes; browser quit keys still work when no dialog is open. Use focus and scrolling for long details.
- **Mouse input does not work**: ensure the terminal supports mouse reporting, or use the keyboard controls.

```sh
bd --readonly --no-color list --all --limit 0 --json
```
