# User guide

ontrack browses Beads issues on a six-column Kanban board with right-side detail and worktree drawers. It can create, edit, move, close after verified integration, or permanently delete one issue at a time. It uses the public `bd` CLI and the current working directory to select the workspace. It does not access the Beads database directly.

## Requirements and startup

- Rust 1.88 or newer to build this Rust 2024 project.
- `bd` available on `PATH`, with support for the JSON commands shown in the [development guide](development.md#beads-cli-contract).
- Run the browser from a Herdr-managed shell, which supplies `HERDR_ENV=1`. Outside Herdr, OnTrack exits before Beads discovery or terminal setup and tells you to open a Herdr workspace. `--help`, `update`, and `uninstall` remain available outside Herdr.
- If no Beads workspace is accessible from the launch directory, OnTrack tells you to run **`bd init`** and exits. Existing workspaces, including inherited and redirected ones, are reused with their configuration intact.
- An interactive terminal supporting raw mode and the alternate screen; mouse support is needed for clicking and wheel input.
- For `ontrack update`, `curl` and `tar` must be on `PATH`, and the executable's directory must be writable for replacement. This command needs neither Herdr nor a Beads workspace.

See the [official Beads documentation](https://beads.gascity.com) for installing `bd` and setting up a workspace. For supported binary downloads and checksum verification, see the [release guide](releases.md).

From this repository, when it is the workspace you want to browse:

```sh
cargo run
```

To browse another workspace, build with `cargo build`, change to that workspace, and launch the built binary using its absolute path. The launch directory, not the binary's location, determines which workspace `bd` uses. Do not launch the interactive application in a runner without a terminal.

After confirming the Herdr launch marker and before opening the terminal interface, OnTrack asks Beads to locate the active workspace. If none exists, it prints “No Beads workspace found. Run bd init in your project, then launch OnTrack again.” and exits successfully. The command **`bd init`** appears in bold on terminal stdout; redirected output contains plain text. OnTrack does not ask setup questions, read input, initialize Beads, or change its configuration. Initialize the workspace yourself, then launch OnTrack again.

Existing workspaces retain their configuration, including JSONL auto-export. OnTrack preferences such as theme, default agent, agent limit and cleanup remain available with `s` in the browser.

If `bd` is missing or workspace discovery fails, OnTrack stops before raw mode and reports the launch directory and failing step. Discovery, permission, and database failures do not trigger initialization guidance or replacement initialization.

A brief splash precedes the browser. A terminal-drawn anime girl blinks and waves beneath the ONTRACK wordmark; narrower terminals use a compact title, and very small terminals show text only. The animation lasts about 1.2 seconds and uses the selected theme. Issue loading starts in the background; quit keys work during startup too.


## Your first task

Once the browser opens in your Herdr project workspace:

1. Use `←` / `→` to choose a column and `↑` / `↓` to select a Bead. Press `Enter` to open its detail drawer; press `Enter` again, `Tab`, or `Esc` to return to the same board selection. Arrows and Page keys scroll the description, comments, and relationships.
2. Press `n` to create a task, or `e` to refine the selected Bead. Give the agent a clear description and choose its harness. Use `Shift+N` on an open task to split off a child task.
3. Move the task to Ready with `Shift+←` / `Shift+→` or choose Ready with `m`. Run the scheduler from the main checkout; it waits for eligible work, an available agent slot, and a usable harness. For an immediate manual handoff, press `h`.
4. Press `w` to open the worktree drawer. `Enter` focuses its Herdr workspace; within this drawer, `m` requests a merge. The agent commits and checks work before signalling Ready To Merge. OnTrack closes the Bead after verified integration, independently of automatic merge/cleanup preferences. Use drawer actions `c` or `x` only to close the integrated workspace or remove its checkout. `Esc` returns to your board selection.

Press `Ctrl+?` whenever you need the controls for the current view. See the scheduling and worktree sections below for eligibility, confirmation, and recovery details.

## Kanban board and moves

All bordered panes and dialogs, including tracked handoffs, forms, and hotkey help, use rounded corners.

Rounded card outlines use issue type colours: bugs are red and features are blue. The selected card keeps its highlighted fill and type-coloured outline, so selection remains clear without hiding the type.

When a dialog is open, the board and any open drawer darken behind it so the
dialog stands out in both Dark and Light themes. Closing the dialog restores the
normal view; standalone help and handoff toasts do not dim the screen.

The full board has six fixed vertical columns, in this order: **Open, Ready, Blocked, In Progress, Ready To Merge, Closed**. Every column shows a count, including zero, and none collapses. There is no Deferred column. Legacy `deferred` and custom statuses remain visible under Open without rewriting existing Beads; the detail drawer retains the raw Beads status. Narrow terminals scroll horizontally to keep columns legible instead of squeezing all six into unreadable widths. Each column scrolls vertically to keep its selection visible.

Use `↑` / `↓` or the mouse wheel to move one card at a time within the focused column, without wrapping at the first or last card. Crossing a viewport edge scrolls only enough to keep the selected card visible, rather than jumping to the top. Each column retains its own scroll position when you switch columns with `←` / `→`, including empty ones. An empty column has no selected Bead for issue actions. `Shift+←` / `Shift+→` moves only the selected Bead to the adjacent column; `m` opens a destination chooser. Moving a parent this way never cascades to children. Moving to Ready allows the existing scheduler to start eligible work; other moves do not start, stop, or restart agents. A confirmed `· sent` handoff marker does not prevent manual backward board moves and still prevents duplicate handoffs through the tracked registry.

Ready means Beads status `open` plus label `ontrack:ready`. Ready To Merge means `in_progress` plus `ontrack:ready-to-merge`; it signals checked, committed work awaiting integration, not completed integration. Moving to Closed or using board shortcut `c` requires freshly verified integration from a tracked handoff into its recorded target. An untracked Bead cannot be closed through OnTrack without that proof. Board moves never authorize destructive Git/workspace operations. Ready borders and text remain blue with a visible label in every theme.

## Browsing and controls

Create Tasks and Epics with `n`, or use `Shift+N` on an open Task to create a child. The create form saves the issue without starting an agent.

### Ready issues and scheduler

Move an individual Bead to Ready for automatic scheduling; its underlying Beads status is `open` with the `ontrack:ready` label. Board moves never toggle descendants. The `r` / `Shift+R` shortcut toggles Ready for an open issue and its open descendants, retaining its existing handoff guards. Those guards do not prevent manual backward board moves merely because a prompt was accepted. Inspect `w` before retrying a failed or uncertain handoff.

Ready changes run in the background, including large Epic cascades. The header shows “Updating Ready for ID…” while processing. You can keep navigating, scrolling, opening help, switching to worktrees, or quitting. Additional Ready changes, mutation dialogs, manual handoffs, and automatic scheduling wait until the update finishes. Confirmed changes appear when processing completes, followed by a live refresh; failures also refresh to show any partially applied changes. Quitting does not cancel a running Ready update.

The new issue form has an Agent harness choice after Priority for every type. It checks Herdr in the background and lists only supported kinds whose integration is current, plus Unassigned. The Default agent for new issues setting controls its initial choice: Automatic selects Codex when available, otherwise the first available kind. A saved agent that is unavailable uses the Automatic fallback for that form without changing the setting. Unassigned starts with no agent selected. This also applies to new child Tasks. Wait for the check before creating an issue. If Herdr cannot be queried or no current integration is found, the form shows the reason and offers Unassigned only; create remains available after the check. A selected agent is saved as an `ontrack:agent:KIND` label; explicit Unassigned is saved as `ontrack:unassigned`. Edit keeps an existing harness choice even if its integration is no longer current. Ready issues with an unavailable selected harness or explicit Unassigned choice do not launch. Older or externally created Ready issues with neither label use the configured default agent when available, falling back to Codex or the first available integration.

New child tasks keep ordinary labels from their parent, but start Open with their own harness selection; they do not inherit Ready, Ready To Merge, harness, or explicit Unassigned markers.

While OnTrack is running from a Herdr main checkout, its scheduler prepares a Ready parent's managed checkout when it has eligible Ready non-Epic descendants, then picks eligible Ready non-Epic issues by Beads priority and ID. Preparing a parent does not start its agent or consume an agent slot. Nested parent checkouts are prepared from the root down so each child branches from its immediate parent. Agents then work from the leaves up: children integrate into their parent branch and close before the parent agent resumes. The scheduler waits for the managed-worktree scan, checks that the chosen harness has a current Herdr integration, and uses the same tracked launch path as `h`. A successful agent handoff leaves an open issue in Ready until its Beads status changes. A prepared Epic can be handed off with `h` after its children integrate. Mark each child Ready separately when using board moves; a child waits until the parent's managed checkout exists. Failed or uncertain attempts show an error and are not retried repeatedly in the same app session. To retry after fixing the cause, turn Ready off and on; inspect `w` first if a worktree may already exist. Starting OnTrack again retries Ready issues that have no recorded handoff.

Ready records your intent to have an issue worked on. Automatic agents also require Beads to report it as dependency-ready (`bd ready`). A dependency-blocked Ready issue stays in Ready and shows `· waiting on BEAD-ID`, listing the blocking IDs returned by Beads; this is distinct from explicitly moving a card to Blocked. Once dependencies clear, the next refresh makes it eligible without another move. A failed readiness lookup pauses scheduling until a successful refresh. Manual `h` remains available. Parent checkouts can still be prepared for eligible children; a dependency-blocked parent agent waits.

The scheduler starts at most five active agents by default. Press `s` and change **Agent limit** to Unlimited or a positive count to set another limit. The choices run Unlimited, 1, 2, 3, and upward. Active tracked handoffs count against the limit even when you started them with `h`; prepared parent worktrees and finished handoffs do not. At the limit, Ready issues wait in their existing priority order until a slot opens. Manual `h` handoffs remain available and can exceed the limit. See the [settings guide](settings.md) for the saved format.

The board lists all returned issues, including closed ones, without the CLI's usual list cap. Closed issues appear newest first by their completion time; if that is unavailable, OnTrack uses the last update or creation time when available. Cards retain issue identity, type, priority, and title. `Enter` opens the selected Bead's right-side detail drawer with its ID, raw Beads status, P0–P4 priority, Markdown narrative, comments, and dependency flow. Miscellaneous metadata and relationship extras remain hidden without changing the underlying data.

Parent-child relationships do not combine board moves: a child in a different column remains there when its parent moves. Closed ordering can place a child above its parent. See the detail drawer for authoritative hierarchy and dependency links.

An Open or Ready issue shows `· sent` beside its status after Herdr confirms the initial agent prompt and OnTrack saves the handoff. The marker survives refresh and restart through the tracked record. Handoff alone leaves the status `open`; an agent or user can change it, moving the card to its corresponding column. The marker does not lock board moves. An uncertain prompt submission does not show the marker. Use `w` to inspect incomplete or uncertain launches.

The caret keeps its display column when possible and stops at the first or last line. New beads default to Task and P2; the harness default follows the saved setting and current Herdr discovery. Settings load/save errors remain visible; failed saves preserve the last successfully saved settings. See the [settings guide](settings.md) for recovery.

## Details, loading, and refresh

Opening a selected issue's detail drawer uses its cached list record while a richer `bd show` request runs. The returned detail record replaces that snapshot. ontrack requests long details, comments, and dependents; descriptions, notes, design and acceptance text render as Markdown. The drawer shows the issue title, raw status, narrative sections, comments, and dependency flow. Relationship Details and Other Details are omitted, including miscellaneous metadata and relationship extras; the underlying issue data is unchanged. It does not invent missing fields or fetch data outside those CLI responses. Arrows and Page keys scroll content below the visible area.

Dependencies appear as a compact flow chart rooted at the selected Bead. **Blocked by ← prerequisites** lists issues that block the selected Bead; **Blocks → dependents** lists issues the selected Bead blocks. Blocking groups appear first. **Parents** and **Children** show hierarchy separately; other link types retain their type and source field without claiming blocking semantics. Solid branches and node headers use the issue's priority color from your theme, with explicit P0–P4 labels when available; missing priorities are neutral. Each node shows its ID, status and full title without repeated boxes. Eight typical children fit in about 20 chart rows at 100 columns. The chart shows direct returned links, including closed issues, rather than loading a recursive tree. Long labels wrap, tiny panes omit indentation, and larger graphs use the usual detail scrolling. Additional relationship fields and unsupported records are hidden. Unsupported records alone do not produce an empty chart or a no-links message. Empty returned relationship arrays show “No dependency links returned”; absent fields do not imply that the Bead has no dependencies.

ontrack automatically polls the board and selected issue's details in the background, starting another refresh roughly one second after the previous refresh completes. Changes made by another terminal or agent appear without manual input or configuring events, a watcher, or extra dependencies. Slow `bd` commands increase the delay; updates are not instantaneous or event-driven. Successful create/edit/move/close/delete actions trigger an immediate refresh. In the `w` drawer, `r` refreshes tracked worktrees.

Context-specific hints point to `Ctrl+?` for the full key reference. Errors and action notices remain visible without replacing shortcuts; confirmation instructions stay in their dialogs. Worktree recovery actions remain in the drawer. Refresh retains cached cards/details while loading and preserves the selected ID when possible, active column, drawer context, bounded scroll positions, and active form input. Failed refreshes retain the last loaded data alongside the error and retry automatically. An empty workspace still shows all six column headings and zero counts.

## Update OnTrack

Run `ontrack update` from a normal terminal, in any directory. It prints the
running version and checks the [latest stable OnTrack release](https://github.com/ThomasJRyan/OnTrack/releases).
If the version is current or no release is published, it reports that and exits.
If a compatible newer release is available, it prints the version and release
link, then asks `Install this verified release? [y/N]`. Enter `y` or `yes` to
install; any other answer, including Enter alone, cancels before replacement.
The command does not start the browser or require Herdr or Beads.

The updater selects an asset for the current operating system and architecture,
downloads its published `.sha256` checksum, verifies the archive, and stages
replacement beside the running executable. A missing compatible asset,
checksum mismatch, network error, missing `curl`/`tar`, or unwritable install
directory returns an error. The existing executable remains usable if the
command fails before replacement; rerun `ontrack update` after fixing the cause.
The updater does not install Beads or Herdr. Restart any OnTrack session already
running after success; that session continues using its original code.

## Launch an agent with Herdr

Run ontrack inside a running [Herdr](https://herdr.dev/docs) shell in a Git checkout. Herdr must supply `HERDR_ENV=1`; `herdr` and the selected agent executable must be on `PATH`, and that agent's Herdr integration must already be installed and current. ontrack does not install integrations or grant Git safe-directory trust automatically.

Codex launches trust the verified main repository and disable startup update checks **for that invocation only**; no global configuration is changed. Source and new-worktree Git metadata must agree before Codex starts. OnTrack also passes `--dangerously-bypass-hook-trust`, so enabled user, project, session, and plugin hooks can run without a separate review for this invocation. Starting a Codex session through OnTrack therefore assumes you trust those hook sources. Saved hook approvals, sandbox settings, and tool approval policy are unchanged. Use a Codex version supporting this flag (verified with 0.163.0). OpenCode startup is unchanged. Authentication, administrator policy or unknown startup prompts may still need your attention; ontrack does not bypass them. Nonstandard or mismatched Git metadata stops startup safely and preserves any created worktree for inspection.

Handoff uses the selected bead and its mapped Herdr workspace, not global window focus. Pressing `h` starts discovery and launch without further input. If the Bead has an agent harness choice, OnTrack requires that exact current Herdr integration. Older Beads without a choice use Codex when available, then the first available integration. Discovery failure can be retried with `h` after resolving the cause. A valid launch creates a worktree from committed checkout content only, starts the chosen integration, and sends the issue context with instructions to inspect the authoritative bead and project guidance. The prompt asks the agent to commit and check finished work, then set status `in_progress` and label `ontrack:ready-to-merge`. It explicitly forbids closing the Bead before merge. Blocked or unfinished work keeps the Bead open or in progress and reports the blocker.

If the description contains screenshots pasted through OnTrack, the initial agent prompt lists their local file paths and asks the agent to inspect them. Herdr sends a text prompt, so the image bytes stay in the shared Beads workspace; the new worktree can read them from there on the same machine.

For child tasks, press `h` on the parent after creating children. OnTrack prepares its worktree without starting an agent while children are open or their worktrees await integration. Then hand off each child; it starts from the parent branch, and its merge target is the parent worktree. Tracked child handoffs appear beneath their parent. Once a child signals Ready To Merge and its agent settles, OnTrack requests merge into the parent worktree automatically by default, including for Epic subtasks and nested children. The child closes only after verified integration into that parent branch; it need not wait for the parent's later integration. Keep OnTrack running so reconciliation can finish. “Auto-merge child tasks into parent” turns automatic requests off; drawer `m` remains available for a confirmed manual request. Top-level automatic merge remains off by default. Git, agent, and Beads safety checks still apply; conflicts or uncertainty stay visible for recovery. Once each child is integrated and closed, press `h` on the parent again to start its agent in the prepared worktree. Parent merge requests also wait for children. A child's handoff asks you to prepare its parent first if needed. Beads disallows a blocking edge from parent to descendant because it would also block the child, so OnTrack enforces the child-first gate itself; external Beads clients do not inherit it. Adding a child cannot pause an already-started parent agent, but parent integration remains guarded. Keep the parent checkout clean before child work and remove child checkouts before parent cleanup.

Only handoffs recorded by OnTrack are managed in the worktree drawer; pre-existing worktrees are not adopted. The target branch comes from verified repository state and is shown before a merge request. Git integration—not Beads status—determines whether work is integrated. Conflicts and uncertain outcomes remain visible for manual recovery. Cleanup never force-removes a checkout or removes its branch.

Verified integration closes a tracked Bead even with automatic merge and cleanup disabled, including when reconciliation detects an external or confirmed manual merge. If Git integration succeeds but Beads closure fails, OnTrack retries closure without replaying the merge and does not clean up prematurely. Already-closed legacy pre-merge handoffs are not bulk reopened or treated as proof of integration; their recorded work remains available for conservative recovery.

Worktree discovery runs quietly in the background. The list stays blank during an initial scan and keeps existing rows visible during refresh. Empty-state guidance appears after a scan completes with no outstanding handoffs and stays visible during automatic refreshes, manual refreshes, and error retries without blinking; scan errors still appear in the header.

A board card enters Ready To Merge from its Beads status and label; that is distinct from the worktree drawer's Git/agent classification. The drawer shows `READY TO MERGE` only when the new readiness signal, settled recorded agent after prompt activity, and clean task commits outstanding against the target support it. An active checkout otherwise remains `IN PROGRESS` or shows the applicable Git/recovery state. Older handoffs can retain their recorded activity evidence for display and conservative recovery; automatic reconciliation still requires trustworthy native-session evidence. If unavailable, inspect the work before a confirmed manual merge. Neither readiness display proves integration nor bypasses Git and agent checks. Legacy pre-merge closure is not the new readiness signal.

If Herdr confirms that the recorded agent session is `blocked` or `error`, an otherwise `IN PROGRESS` tracked checkout shows `BLOCKED` and the details name the observed state. The label returns to `IN PROGRESS` when that observation clears or becomes unavailable. Git states such as uncommitted changes, merge conflicts, and completed integration keep their own labels. This display label does not change the Bead's status or grant permission to merge, retry, or clean up; inspect the agent pane and Bead to recover the task.

In the `w` drawer, select a handoff with Up / Down and press Enter to focus its recorded Herdr workspace. This uses the existing workspace; it does not create or reopen one. Closed workspaces cannot be focused. The drawer keeps all-handoffs recovery access even for work unrelated to the selected board card. Details use the refreshed Bead title/description when available, otherwise the captured handoff text or an unavailable-text fallback, alongside Git/Herdr state. PageUp / PageDown scroll long details. Press `m` to request merge, `c` to close an integrated Herdr workspace, or `x` to remove an integrated checkout; each requires `y` confirmation. Manual and automatic requests enter a durable repository queue. `MERGE QUEUED` waits while another merge is active; only the first request is sent to its agent. After verified integration and a settled prompted agent, the next request is rechecked against live Git, Beads, and Herdr state. Resolution errors or uncertain prompts hold the queue for explicit recovery. Retry a reviewed queue error with `m` after fixing its cause. The agent merges the target into the task branch and resolves conflicts there; OnTrack verifies history and fast-forwards the target. Keep OnTrack running for reconciliation. `r` refreshes worktrees; `Esc` closes the drawer and restores board selection.

Press `a` on an active tracked handoff to ask its original idle agent to continue in the same checkout. Confirm with `y`; `n`, Enter, or Esc cancels. OnTrack checks the live Bead, checkout and Herdr workspace ownership, native agent session, idle state, and agent checkout paths before sending one prompt. It preserves commits and uncommitted changes. If the agent exited, changed session, is busy, or cannot be verified, inspect its Herdr pane or use the confirmed fresh start below. If prompt delivery is uncertain, the row stays Needs Attention across restarts and OnTrack will not send another prompt; inspect Herdr before manual recovery. This action does not close the Bead or authorize a merge.

Press `Shift+R` on an active tracked handoff to restart its task. The dialog identifies the handoff and warns that confirmation with `y` discards all uncommitted checkout changes and closes the current Herdr workspace; `n`, Enter, or Esc cancels without touching Git or Herdr. OnTrack verifies the recorded checkout and workspace, force-removes that worktree, and launches the same live Bead with the recorded agent in a fresh branch from the current main checkout HEAD. The Bead and its status are retained, and the abandoned branch is kept for recovery. Restart is independent of integration status, unlike normal cleanup. If removal or relaunch is uncertain, the old record remains visible as Needs Attention; inspect the reported Herdr and Git state before taking manual recovery action. OnTrack never blindly repeats a restart.

Once OnTrack verifies checkout removal, that handoff leaves the `w` drawer immediately and stays hidden after refresh or restart. The record remains in the local registry. A removed child stays hidden after its parent Epic checkout is merged and removed: OnTrack checks the retained child and parent branches to confirm the child is still integrated. If the child branch gains new commits, a recorded path reappears, or that history cannot be verified, its `NEEDS ATTENTION` status makes it visible again. A closed Herdr workspace with its checkout still present remains visible.

OnTrack also checks recorded checkout paths during its regular worktree refresh. If a managed checkout was removed with Git or another external action, it records the missing checkout and removes it from `w` without requiring an automatic cleanup preference. This only tracks the checkout path: the source branch is retained, and its commits may still need integration. Check Git history before deleting that branch. A path that reappears is shown as `NEEDS ATTENTION` for identity review.

Worktree statuses appear as coloured text in both the list and details, on the pane's normal background. Merge Pending uses the theme warning colour, Integrated uses success, and states needing attention use danger. Other labels use the theme's info, secondary accent, or muted colours. The words remain visible, including when a row is selected, so colour is not the only state cue.

Ordinary uncommitted changes in either the task checkout or its target show `UNCOMMITTED CHANGES`, rather than `NEEDS ATTENTION`. The detail asks you to commit or resolve them before merging or cleanup. A merge request already in flight stays `MERGE PENDING` and includes the same warning. These labels do not make a dirty checkout eligible for a merge or cleanup; those actions still check that both checkouts are clean. Checkout identity errors and unfinished Git operations continue to need attention, and unresolved merge conflicts retain `NEEDS RESOLUTION` during a merge request.

During a requested merge, Git may briefly contain unresolved files or the target branch may advance while the agent is still working. When Herdr confirms the recorded agent is working, OnTrack keeps the label at `MERGE PENDING` and shows the Git concern in the details. If the agent is idle, done, blocked, or cannot be verified, the same unresolved Git state shows `NEEDS RESOLUTION`. That label calls for inspection; it does not mean OnTrack has verified that the agent failed. A pending label does not make the worktree eligible for integration or cleanup.

An unfinished merge of the recorded target HEAD in a managed source checkout shows `MERGE IN PROGRESS` even when it was started outside an OnTrack merge request. The detail distinguishes unresolved conflicts from an unfinished merge without conflicts. This label describes Git state; resolve and commit or abort the merge before requesting integration. A merge against another commit, an unfinished operation in the target checkout, or an invalid checkout identity still needs attention. OnTrack merge requests continue to use `MERGE PENDING` and `NEEDS RESOLUTION` as described above.

Agents can report activity from their managed source checkout with `ontrack status working`, `ontrack status merging`, or `ontrack status blocked 'brief reason'`. Run `ontrack status clear` when the activity ends. A detail is optional for working and merging and limited to 200 characters on one line. The report appears in the tracked-worktree details for 15 minutes, then expires unless refreshed. The command refuses an unmanaged, inactive, or mismatched checkout. Reports are advisory and never change Beads, Git, merge eligibility, or cleanup eligibility. If `ontrack` is not on the agent's PATH, invoke the installed executable by its absolute path.

Untouched branches with no task commits are not automatically considered complete. Herdr can report the native agent session after startup; OnTrack recognizes it on a later refresh when the saved launch terminal, lifecycle activity, and checkout still match. If that evidence is missing or changes, automatic operations defer and the worktree details show why. An explicitly confirmed manual merge can use Git verification without optional session metadata. Removal also closes an open Herdr workspace, so enable removal before closing if both are wanted. Removal after a workspace has already been closed is unsupported: inspect the reported checkout, verify its current changes are integrated and clean, then use Git's exact-path, non-force worktree removal manually. OnTrack never guesses a replacement workspace ID.

Title-only or incomplete beads are supported: the agent is instructed to infer a useful description, scoped requirements and testable acceptance criteria from the live bead and project context, record assumptions, and save missing fields with `bd update` before implementation. It must preserve existing requirements, avoid unrelated scope, and not refuse solely because description or criteria are missing. Only consequential ambiguity unresolved by context warrants clarification; useful inferred details, assumptions and questions should still be saved first. ontrack sends these instructions rather than generating fields itself; handoff success does not prove the agent followed them.

Start ontrack from the **main checkout** (or an ordinary subdirectory) to hand off work. Launch discovery from existing linked checkouts, submodules or nested repositories is unsupported and stops before creation; Herdr 0.9.1 reports the main source checkout for linked paths, so ontrack will not guess a linked workspace. Newly created worktrees remain the verified targets for agent startup.

Contributors can run `cargo test` from a linked Git worktree. The Herdr test fixtures model a main checkout independently of the directory where Cargo runs; this test support does not change the launch restriction above.

The new checkout contains committed Git content only; uncommitted changes are not copied. A successful handoff does not mean the agent completed the bead. Failures may leave a worktree or may have delivered a prompt. Inspect Herdr/Git worktree lists and the reported workspace/branch before retrying; nothing is automatically deleted or blindly resubmitted.

The top-right toast stays visible during discovery and launch, then shows success for seven seconds or failure for fifteen seconds. A successful agent handoff reports the agent, workspace, pane, and branch. The second header row also shows the result or error while space permits, and `w` shows recorded worktrees for recovery. Compact terminals shorten the toast with a pointer to tracked worktrees. If a failure may have created a worktree or sent a prompt, inspect the recorded and Herdr/Git state before pressing `h` again.

Discovery and each handoff run independently of browsing and managed-worktree actions. You can select another Open task and press `h` while an earlier handoff is still running. The newest handoff owns the toast; an older result does not clear another pending launch. While handoffs are pending, tracked-worktree refreshes use a read-only snapshot so display checks do not hold the registry lock needed to record another launch. Ready scheduling includes pending manual/automatic launches in the agent limit; preparing a parent checkout does not consume a slot. Board moves do not cancel pending or accepted launches, and the durable registry still guards duplicates. Durable records and recovery evidence survive restart; pending/toast state is session-local. A managed merge can still hold the registry lock: launch journal writes retry contention for about two seconds, then fail safely rather than bypassing it.

The `w` details include a separate display-only agent observation such as working, blocked, idle, error, or unknown. It is refreshed independently about two seconds after each poll completes. Missing or mismatched recorded-session evidence and poll failures show unknown without discarding the worktree or recovery details. An agent observation—even done—is not proof the Bead completed, and never authorizes retry, merge, or cleanup; the existing Git, Beads, and original-agent safety checks still apply.

Backend work does not run on the terminal input loop, so browsing remains responsive while a command is slow. Handoff keeps the browser usable; create, edit, close, and delete mutations still lock their dialogs until a result arrives. Worker requests are queued and executed in order without coalescing. Quitting restores raw-mode, mouse-capture, and alternate-screen settings through the application's cleanup path.

## Troubleshooting

- **“Could not run bd”**: check that `bd` is installed and on the launch environment's `PATH`, including when starting from an editor or a different shell.
- **“bd failed” / workspace or database errors**: check the error text and launch directory. Run the read-only list command below from that same directory to diagnose the CLI separately; consult the official Beads documentation for workspace access or setup.
- **Unknown CLI options**: ensure your `bd` supports `--readonly`, uncapped listing, and the detail flags in the development guide. ontrack reports failures rather than silently dropping those flags.
- **Invalid JSON or malformed records**: list/show responses must be JSON arrays; creation must return an object with an ID. List entries need nonempty string IDs, titles, and statuses. Check the command output and your CLI version.
- **“expand terminal” / clipped content**: use Left / Right to reach off-screen board columns and Up / Down for cards. Detail drawers use arrows / Page keys. Enlarge the terminal if it cannot fit a legible column or dialog; quit keys still work when no dialog is open.
- **Mouse input does not work**: ensure the terminal supports mouse reporting, or use the keyboard controls.

```sh
bd --readonly --no-color list --all --limit 0 --json
```
